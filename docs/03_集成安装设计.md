# 调研报告 3:vdriver 集成与安装设计调研

> 调研代理 3 产出。SONAME/DT_NEEDED 结论来自 /tmp 下独立实验,未触碰仓库。

## 一、链接事实
- **默认链桩**:`runtime/src/runtime/cmake/runtime.cmake:499-500`——Windows 链真 `ascend_hal`;Linux 且 `ENABLE_TSD!=true` 链 `ascend_hal_stub` 目标(592、687 同式,tiny/v200.cmake 同)。`ENABLE_TSD` 仅存在于这 3 个 cmake,build.sh 不设它 → 开源构建默认=链桩。
- **桩目标**:`cmake/stub/CMakeLists.txt:23-71` 用 h2c.py 把 `ascend_hal{,_external,_base}.h` 全量转成桩 C(`:29-41`),`OUTPUT_NAME=ascend_hal`(`:56-59`),安装到 `${INSTALL_LIBRARY_DIR}/stub` 与 `lib/${arch}/stub`(`:66-71`);`ENABLE_OPEN_SRC` 下 `ascend_hal` 是 stub 的 ALIAS(`:61-63`)。
- **DT_NEEDED 记 soname 而非路径**(实测):CMake SHARED 目标(无 VERSION)自动加 `SONAME=libascend_hal.so`,链接它的目标 DT_NEEDED=`libascend_hal.so`。libruntime 运行时按名字找。
- **搜索序**:非 COV/UT 构建 `CMAKE_SKIP_RPATH TRUE`(`cmake/func.cmake:386`),包内无 RPATH → `LD_LIBRARY_PATH` → ld.so.cache → 默认目录;stub 装在 `lib/stub` 子目录、真驱动装在 driver 包,谁先命中由环境变量决定。

## 二、三种替换选项对比与推荐
- **a) 同名替换(推荐)**:vdriver 构建为同名同 SONAME 的 `libascend_hal.so`,置于 LD_LIBRARY_PATH 更前或直接替换 `lib/stub/libascend_hal.so`。DT_NEEDED 弱符号直链(`npu_driver_base.hpp:15-233`)加载期即绑到 vdriver;4 类 dlsym 消费者同文件命中;零源码改动、不进官方 cmake、升级重装 stub 不冲突。代价:必须补齐全量导出。
- **b) 改 cmake 换目标**:runtime.cmake:500(及 592/687、tiny.cmake:545/648/739/868、v200.cmake:616/723 共 9 处)的 `ascend_hal_stub` 换成 vdriver 目标。侵入源码、分散 3 个 cmake,升级必被覆盖,还要处理 stub 的 install 规则。仅建议作 CI 出包形态备选。
- **c) LD_PRELOAD 强符号抢绑**:ELF 全局符号序为 可执行→LD_PRELOAD→DT_NEEDED 广度优先,weak 未定义引用会绑到 preload 中的强定义,机制成立;但 4 个消费者 `dlopen("libascend_hal.so")` 会按名字命中**已加载的桩**(plog/trace/awatchdog/msprof 全中招),除非 vdriver 也设 `SONAME=libascend_hal.so` 并先于 stub 加载(glibc 按名称/soname 匹配已加载对象,此行为未实测,建议 preload 后 `dlopen`+`dlinfo` 验证句柄归属)。分裂风险大,不推荐。
- **结论:选 a**。最小侵入、单一 .so、语义统一。

## 四、SoC 命名传导链
`halGetSocVersion`(weak,`api_c_soc.cc:29`、`runtime.hpp:31`)→ `Runtime::InitSocVersionByDrvSocVersion`(`runtime.cc:655-696`,经 `GetChipTypeFromPlatform` 定 chipType)→ `GlobalContainer` → `rtGetSocVersion`(`api_c_soc.cc:51-88`)→ acl `InitSocVersion`(`acl_rt_impl_base.cpp:122-135`)→ `aclrtGetSocNameImpl`(`:204-216`)→ `fe::PlatformInfoManager::InitRuntimePlatformInfos(socVersion)`(`:46-53`;`platform_info.cpp:1260-1287`)加载 `<libplatform.so 所在目录>/data/platform_config/<SoC名>.ini`(`platform_infos_utils.h:23,65-79`,包内源 `src/platform/platform_config/cann/*.ini`)。

opbase 侧 `aclrtGetSocName`(`opbase/src/nnopbase/composite_op/aclnn_engine/op_kernel_lib.cpp:146`)与 `rtGetSocSpec("version","NpuArch")`(`utils/platform.cpp:304`;实现 `api_c_standard_soc.cc:1664-1686`,经 `PlatformManagerV2::GetSocSpec` 读**同一 ini**)决定 tiling/选核;chipType 由 ini 的 `[version] Chip_type` 映射(`soc_info.cc:23-37`、`platform_config_keys.h:17,20`,如 Ascend310B1.ini `Chip_type=7`)。

**结论**:ini 只是"名称→规格"映射,不兜底名称本身;名称兜底链是 ①用户显式 `rtSetSocVersion`(`api_c_soc.cc:89`)②halGetSocVersion 缺失时按 `INFO_TYPE_VERSION` 硬件版本+chipType 推导(`runtime.cc:697-731,611-648`)。**vdriver 必须报一个存在对应 ini 的真实型号(建议 Ascend910B1),否则 tiling 在 InitRuntimePlatformInfos 报错返回。**

## 五、VIRTUAL/PHYSICAL 决策
`INFO_TYPE_RUN_MACH` 的读点仅 `npu_driver.cc:85-89`(连同 `INFO_TYPE_ADDR_MODE`);`sysMode_` 消费点全仓仅两处:①`npu_driver_res.cc:1562-1565`——VIRTUAL 且 addrMode_!=0 时 cqeDepth 强制 256(`npu_driver_base.hpp:240,271`);②`RUNTIME_WHEN_NO_VIRTUAL_MODEL_RETURN` 宏(`:271-273`)→ `npu_driver_mem.cc:288,302` 的 HostAddrRegister/UnRegister(仅 hccs/smmu agent 模式需要)。**本报告建议报 PHYSICAL(0)+ADDR_MODE_INDEPENDENT:两处分支全部走普通路径,复杂度最低;报 VIRTUAL+独立地址模式等价,无额外收益。**

(汇总说明:报告 1 建议 VIRTUAL+flat 以少实现 2 个弱符号并缩小 CQ 深度;两者皆可行,实施方案.md D4 采 VIRTUAL+flat 为主、PHYSICAL 为 fallback。)

## 六、多设备/进程建议
单 .so 多进程各自独立映射,库内全局态不跨进程泄漏;建议 vdriver 句柄表每进程一份、进程内加锁(含 fork 后子进程重初始化,可参考 `awatchdog_core.c:63-70` 的 pthread_atfork 惯例);跨进程语义接口(halShrId*/halMemShare*,`npu_driver_base.hpp:111-115,86-97`)直接回 `DRV_ERROR_NOT_SUPPORT` 走降级(`npu_driver.cc:80-84`)即可。
