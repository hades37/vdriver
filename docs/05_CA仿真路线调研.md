## 三、实证结果(✅ 已跑通,数值正确,2025-09-01)

**最终配方(PV 变体,干净收尾 exit=0)**:
```
libruntime.so    → simulator/Ascend910B1/lib/libruntime_cmodel.so   (PV runtime)
libascend_hal.so → simulator/Ascend910B1/lib/libnpu_drv_pvmodel.so  (PV 驱动)
LD_LIBRARY_PATH=/tmp/ca_lib:$TK/lib64:$SIM/lib:$TK/../lib64, cwd=$SIM
```
hello_cann 结果:**exit=0,"Sample run successfully!",8/8 数值匹配**
(result 1.5/3.0/…/12.0 —— 内核 x86 真仿真执行),"ACL finalize successfully"。

过程要点(踩坑记录):
1. **符号 interposition 是最大坑**:libopapi/libnnopbase 的 DT_NEEDED
   libascend_hal.so 一旦被真包/自研 hal 满足,其 hal*/drv* 符号会抢先绑定,
   CA 驱动被整体绕过(表现为 halSqCqAllocate ret=3)。解法:libascend_hal.so
   直接软链到仿真驱动自身,单一实现,零分流;
2. runtime 源码仓的 cmodel_driver(调 startModel)与 toolkit 预编译驱动**版本
   不一致**(源码引用 tsRegDrvReportIrqTriger 等本包不存在的符号),预编译驱动
   自包含(仅 libc 未定义)——直接用预编译件;
3. 官方构建脚本 `build_runtime_cmodel_product.sh --product_type=ascend910B1`
   可完整编出源码版 runtime_cmodel/camodel(含第三方 protobuf/abseil 源码编译,
   约 20 分钟),但产物驱动与 toolkit 仿真模型库符号不兼容,当前以预编译件为准;
4. CAMODEL 变体(libruntime_camodel + libnpu_drv_camodel)同样数值正确,但
   进程收尾 double-free(官方栈内部问题),PV 变体干净——以 PV 为准。

## 四、与 vdriver 的定位对比

| | vdriver(假 HAL) | CA/CAMODEL(官方仿真) |
|---|---|---|
| 内核执行 | 不执行(数值非目标) | **x86 真仿真执行,数值正确** |
| 形状数据依赖算子(nonzero/topk 路由/掩码) | 全部踩坑,需 host 回退 shim | 应原生支持 |
| 维护方 | 自研(语义缺口自担) | 官方(cmodel_driver + 仿真模型随包) |
| 速度 | ~原生 | 慢 2-4 个数量级(整芯片 CPU 模拟),仅适合算子/小网络级 |
| 大模型训练(Kimi-K3) | 流程可推(待收口) | 不现实 |
